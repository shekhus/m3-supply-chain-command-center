# Design decisions — M3 Supply-Chain Command Center

One entry per decision that changes behaviour: what was decided, what else was considered, why, and the
evidence. Newest last. Project A's log is in `m3-trusted-data-foundation/docs/decisions.md`; decisions shared by
both repositories are recorded in whichever repo implements them and referenced from the other.

### B-001 · 2026-09-16 · Scaffold reuses Project A's proven infrastructure, with its own data model and ports

- **Decision:** the repository starts from the parts of `m3-trusted-data-foundation` that are already proven in CI and production, copied rather than imported: the numbered plain-SQL migration runner (`db/migrate.py`, advisory lock, checksums), settings loaded from the environment with a `.env` that wins over the shell, the server-side role dependency (`app/auth.py`), the lint runner, the repo-hygiene guard and its banned-term list, and the GitHub Actions workflow.
  - **What differs, deliberately:** schemas are `gold`, `metrics` and `ops` (no medallion bronze/silver: this system reads gold and never ingests); settings carry `GOLD_SOURCE` (standalone or external), `POLICY_FILE`, `JIRA_MODE` and console URL; the local stack publishes Postgres on **5433**, the API on **8010** and the console on **8511**, so it runs beside Project A without a port clash; the database is `m3cc`.
  - **Copied, not imported.** The two repositories stay independently runnable and deployable; a shared library would make Project B unable to start without Project A, which is exactly what B14 (standalone mode) exists to prevent.
  - The public plan and the addendum are the same files as in Project A, retitled: one governing document, two copies, no divergence.
- **Alternatives:** a shared internal package for the common infrastructure (couples the repos and complicates deployment for perhaps 300 lines); starting from scratch (re-solving migrations, config precedence and CI for no gain); reusing Project A's ports (the two stacks could not run side by side, and every demo needs both).
- **Reason:** CLAUDE.md's session ritual and the plan's week-6 definition of done. **Verified:** migrations create the three schemas, re-running is a no-op, an edited applied migration is refused, and a non-Postgres URL is rejected; lint is clean; the repo-hygiene guard scans every text file for engagement-identifying terms.

### B-002 · 2026-09-16 · Standalone gold from the same world as Project A, with a self-check that fails generation when a seeded anomaly is absent

- **Decision:** `make synth-gold` (`python -m synth.generate_gold`) builds gold here, so this repository runs and demos without Project A (plan B14).
  - **The same world, not a second one.** `synth/{config,world,events,gold}.py` are copies of Project A's generator modules, run with the same seed, so both repositories produce the identical population: same plants, customers, items, order lines, yield runs and inventory snapshots. `synth/anomaly_truth.py` keeps only the anomaly parts of A's `truth.py` (the window-versus-baseline check and the answer-key writer).
  - **Six seeded anomalies** carry over unchanged: A1 lane-level OTIF collapse (PLT-02 → C000031), A2 weight-basis fill-rate shortfall (PLT-01 CASE-READY, invisible on the count basis), A3 yield shortfall (PLT-03 L2 PRIMALS), A4 stalled lots ageing at DC-EAST, **A5 the holiday decoy** (a real dip that a day-of-week and holiday aware detector must not raise as HIGH), and A6 a backlog build-up at PLT-02.
  - **The self-check is a hard gate.** Each anomaly is recomputed at its own grain against a 56-day baseline, and generation writes nothing to `ground_truth/` and exits non-zero if an effect is missing or points the wrong way. Detection recall, precision, lead time and attribution accuracy are all scored against that file, so a ground truth that lies would invalidate every later measurement silently.
  - The generator also writes its pandas daily metrics to `data/metrics/`. They exist to support the self-check and to cross-check the SQL metric layer (B-3); the system itself reads `metrics.daily_*` in Postgres, never these files.
- **Alternatives:** importing Project A's `synth` package (B could then not run without A, which is exactly what standalone mode exists to prevent); writing a fresh world for B (the two projects would stop telling one story, and A's answer keys would no longer describe B's data); reading A's published gold only (no standalone demo, and B's evaluation would depend on A's pipeline being run first).
- **Reason:** plan §3.4 B14 and the week-6 definition of done. **Verified (`tests/test_generate_gold.py`):** the build is deterministic for a seed and differs for another; gold carries every column the metric layer needs; all six anomalies are measurably present, with the decoy a genuine −0.19 dip; the answer key and manifest are written with observed values and exactly one `expect_detection: false`; flattening the A1 series makes the self-check fail loudly; and **B's `fact_delivery` fingerprint equals Project A's row for row** when a sibling checkout is present. Live run: 51,571 delivery rows, 26,202 inventory snapshots, 6,175 yield runs, self-check passed for all six.


### B-003 · 2026-09-16 · Metric definitions live in numbered plain SQL, recomputed from raw fields and cross-checked against the generator

- **Decision:** every number this system will ever narrate is computed by `metrics/sql/*.sql` — plain, numbered, idempotent SQL run in order by `metrics/runner.py` (`make metrics`) into seven `metrics.daily_*` tables, one per grain a detector can work at: total, plant, lane (plant × customer), plant × product group, backlog by plant, yield line, and inventory location. No LLM, no Python arithmetic, no notebook. A metric changes by editing one file that a reviewer can read.
  - **The SQL recomputes on-time and in-full from the raw fields** (`010_delivery_flags.sql`) rather than trusting the flags published in gold, and a test asserts the two agree for all 51,571 rows. That proves this project implements the same definition rather than assuming it — the failure mode where two systems quote the same KPI and mean different things.
  - **Constants come from `policy.yaml`, never from the SQL.** `metrics.constants` is loaded from `policy.metrics` before every run (catch-weight tolerance 2%, at-risk window 5 days), because a `CREATE VIEW` cannot take a bind parameter and a tolerance hard-coded in three files is a tolerance that will one day disagree with itself. The same file carries the thresholds, seasonality (28-day baseline, the holiday list containing A5's week), allowed actions and limits that weeks 7–9 read.
  - **Each file merges by its own key**, so recomputing one day is idempotent and never duplicates a row; `metrics.runs` records the window, the per-table row counts and any error, which is the freshness the brief must disclose (principle 3).
  - **The generator's `_anomaly_id` marker column is deliberately NOT part of gold** and is dropped on load: it is answer-key material, and a detector able to read it would be scoring itself.
  - **Backlog is a continuous daily series** — a row per plant per calendar day, including days with no shipments — where the generator's pandas version emitted only days that had shipments. A queue of zero is a fact a detector needs; a missing row would silently break a consecutive-days rule.
- **Alternatives:** dbt (a second toolchain and a second definition language for eight models); computing metrics in pandas at request time (nothing to test independently, nothing to index, and the detectors would depend on a Python process rather than on data); trusting gold's published flags (faster, and it hides exactly the disagreement this project exists to catch).
- **Reason:** CLAUDE.md principle 1 and the week-6 definition of done. **Verified (`tests/test_metrics_sql.py`, 17 tests):** all seven SQL series equal the generator's independent pandas recomputation to 1e-9 on every shared key; the recomputed flags disagree with gold's published flags on 0 of 51,571 rows; A1's lane and A2's weight-basis shortfall are measurably present in SQL, with A2 still invisible on the count basis; rerunning a window leaves every table byte-identical; `gold.*` has no `_anomaly_id` column; a misnamed metric file and a policy missing a section are both refused. Live run: 561 / 1,677 / 15,638 / 8,229 / 1,692 / 6,175 / 940 rows over 2025-03-01 .. 2026-09-15.

### B-004 · 2026-09-16 · Three detectors in code, severity as the strongest verdict, and four gates that decide what is worth a morning

- **Decision:** anomalies are found by three independent detectors in `detect/`, all pure code, and no module under `detect/` may import an LLM — a test enforces it (principle 1).
  - **Baseline** (`baseline.py`): a 28-day rolling window, **de-seasonalised by weekday** before the z-score. Comparing a Monday against a mean containing four Sundays produces a signal about the calendar, not the business. Holidays are excluded from the window so a shutdown does not quietly lower the bar for the fortnight after it. A policy floor under the standard deviation stops a flat series producing an enormous z on its first ordinary wobble.
  - **Threshold** (`threshold.py`): the hard lines from `policy.yaml`, in three shapes — absolute level, absolute magnitude (yield variance is bad in both directions), and z relative to the segment's own history (400 open backlog lines is routine at one plant and alarming at another). Each fires only after its `consecutive_days`, and **a missing day breaks the run**: a metric that was not published is not evidence of a breach.
  - **CUSUM** (`cusum.py`): accumulates standardised deviations and fires at the policy's decision interval, catching a half-sigma drift that never trips the z detector on any single day — the shape of A2 and A4. It reports the **change point**, which is what lead time is measured from and what the brief says out loud.
  - **Severity is the strongest thing any detector said**, then capped by four gates: thin volume (a rate from three lines is arithmetic, not information), immaterial movement (a 1-point move on a 99% series is 6 sigma and nobody's morning), **no corroboration** (the baseline alone sees one day; HIGH needs consecutive days or an accumulated shift), and the **holiday allowance** — a day inside a holiday window is capped at WARN. The dip is still reported, never deleted.
  - **Detectors only speak in the direction that is bad for the metric.** OTIF at 100% is a good day; a detector that reports it teaches people to stop reading the brief.
  - **Ranking is dimensionless**: how many *material* moves it made (the policy's own `min_magnitude` is the unit), times how big the segment is next to a typical one at that grain. Ranking on magnitude × volume in native units means pounds always beat percentage points and the brief leads every morning with whichever metric has the largest unit — a fact about arithmetic, not about the business.
  - **Every grain an anomaly can live at is watched** (11 series over 173 segments): a lane collapse is invisible in the company total, and a weight-basis shortfall is invisible at plant level. That is the failure mode of the dashboard this project replaces.
  - **Some series are threshold-only, by design.** A line that runs four days a week has no 14 clean days in a 28-day window, so it gets no baseline and no `expected`. The brief must then cite the value against the policy line rather than invent an expectation.
- **Alternatives:** a single detector (each one misses a different shape — the cliff, the level, the drift); Prophet/ARIMA or an anomaly-detection library (a second dependency and an unexplainable number, where the whole point is that a VP can be told why something was flagged); an LLM asked "is this unusual?" (principle 1, and unreproducible); ranking by raw magnitude (see above).
- **Reason:** plan §3.4 B2, week-7 definition of done. **Verified (41 tests):** hand-computed z on a paper series; an ordinary Sunday unremarkable with the weekday adjustment and flagged without it; a holiday collapse never entering the mean; the consecutive-day rule refusing to bridge a missing day; CUSUM catching a drift whose every day is below z=3, staying silent on a wobble, and ignoring the 4 July week; each gate capping in isolation; and against the answer key — **A1, A2, A3, A4 and A6 all reach HIGH inside their windows, lead times 0/0/1/4/7 days, and A5 is reported but capped at WARN, where the same detectors with `known_holidays` emptied raise it HIGH.** Over the full 535-day window: 9,265 findings, 1,793 at WARN or above, 932 HIGH (1.7 a day). Precision and recall against the answer key are scored in B-6, and the floors will be tuned there with measured numbers rather than guessed at here.

### B-005 · 2026-09-16 · Attribution by exact rate/mix decomposition, ranked by who got worse

- **Decision:** `detect/attribute.py` decomposes an anomaly's movement into the finer segments underneath it, in code. A rate at a coarse grain is a weighted average of the same rate at a finer one, and the movement between two windows splits exactly:
  - `R₁ − R₀ = Σᵢ wᵢ₁(rᵢ₁ − rᵢ₀)` — the **rate effect**: this segment got worse — `+ Σᵢ rᵢ₀(wᵢ₁ − wᵢ₀)` — the **mix effect**: this segment is a larger share of the volume. The identity is exact, so the contributions sum to the movement being explained. That closure is what licenses printing a percentage at all.
  - **Drivers are ranked by the rate effect, not by the total.** Measured: ranking on the sum made PRIMALS the top driver of A2's shortfall (a volume-mix artefact) and hid CASE-READY, the seeded cause. A short window's volume mix wanders against a 28-day baseline, and those terms are large enough to bury the segment that actually deteriorated. Ranked on the rate effect, the top driver is the seeded segment in every case tested.
  - **The publishable number is `rate_effect_pct`** — the segment's share of the performance change — because a share of the *whole* movement can exceed 100% or flip sign when the mix moved the other way. "PLT-02 accounts for −52% of the drop" is arithmetically true and unpublishable.
  - **When the mix half dominates, the attribution says so** instead of naming a culprit: "the movement is mostly a change in what was shipped, not in how any segment performed". Those are different problems with different owners.
  - **Holidays are excluded, and evidence refs name only days that entered the arithmetic.** A window lying entirely inside a shutdown attributes nothing — naming a driver there would be blaming a lane for a day the plants were shut, which is the A5 mistake wearing a different hat.
  - **An anomaly already at the finest grain held says so** rather than inventing a driver. Backlog and inventory have no finer table, and the honest output is "this is as fine as the data goes".
- **Alternatives:** a single "top segment by absolute change" (ignores volume, so the smallest lane always wins); Shapley values over segments (defensible, far slower, and nobody in the room can check the number); asking the LLM which segment mattered (principle 1 — and it would be a guess dressed as a finding).
- **Reason:** plan §3.4 B3, week-7 definition of done. **Verified (15 tests):** a hand-computed two-lane decomposition (0.90 → 0.70 on half the volume = −0.10, all of it that lane's, zero mix); a pure mix shift where nobody performed differently, correctly labelled and not blamed on anyone; contributions summing to the total movement across four lanes with both rates and volumes moving; a deteriorating lane outranking a steady one with a bigger mix term; a segment appearing in only one window credited the parent's rate so it is never blamed; and against the answer key — **from the plant-level anomaly, the top driver is the seeded lane C000031 (40.4% of the performance change); from the company total it is PLT-02; from PLT-01's fill-rate anomaly it is CASE-READY**, the group whose shortfall is invisible on the count basis. `make detect` now prints the drivers under each incident.

### B-006 · 2026-09-16 · Replay scoring, and what the first measurement said about the thresholds

- **Decision:** `make replay` walks the history day by day with no LLM, merges flags into events, and scores them against `ground_truth/anomalies.json` into a generated `evals/REPLAY.md`. The scoring definitions are written down before the code, because each one can be chosen to flatter the result:
  - **An event, not a flag.** A three-week collapse produces twenty-one flags; counting them separately would make recall effortless and precision catastrophic, and neither number would describe what a person experiences. Runs are merged, bridging gaps of up to three days.
  - **A match needs a shared segment key.** An event at a coarser grain matches — a plant-level drop is the lane collapse seen from further away — but a company-total wobble sharing no key with the seeded segment does not, or every anomaly would be "detected" by a company-level twitch.
  - **Recall at WARN or above, precision at HIGH.** Recall asks whether the system noticed; precision asks whether it interrupted someone.
  - **Lead time is measured from the anomaly's start and never goes negative.** An event already running when the anomaly began belongs to whatever came before it; crediting it would report prescience.
  - **The decoy is scored on its own days.** An event beginning a week earlier that runs into the holiday was raised for its own reasons.
- **What the first run said, and what changed because of it.** The first replay scored **recall 100%, precision 2%** — 383 HIGH events, 377 of them with nothing behind them. Four things were wrong, and all four are worth more than the number they fixed:
  1. **The thresholds in `policy.yaml` were guesses, and the data said so.** OTIF's `high` of 0.90 sits at the measured median of 0.905 — the rule fired on half of all days. `lb_at_risk_within_5d`'s warn of 1,000 sat below its median of 1,410. Every level is now set from the observed distribution (warn ≈ the worst 5% of days, high ≈ the worst 2%), and the percentile is written in the file next to it.
  2. **A line drawn for the company is not the line for one lane.** `threshold_overrides` scopes a rule by grain. A lane's *daily* rate is 0 or 1 — median 1.00, tenth percentile 0.00 — so no absolute line means anything there; a lane is judged on its **seven-day volume-weighted rate against its own 28-day norm**, compared like with like, which is the number an operations lead would use.
  3. **An incident is a policy breach, not a statistical shift.** The baseline and CUSUM detectors can raise WARN on their own — something moved, someone should look — but only a line in `policy.yaml` makes it HIGH. Without this rule the statistical detectors produced 322 of 365 HIGH flags, nearly all of them real movements nobody needed waking for. Statistics say a thing changed; policy says it matters.
  4. **CUSUM never reset after signalling** — a genuine bug against the textbook procedure, which left the statistic above the decision interval for as long as a shift lasted and reported the same change every day for a fortnight.
  - Also: **a holiday cannot extend a breach run.** A four-day shutdown was handing the consecutive-day rules their days for free, so the first trading day afterwards — backlog still clearing — became an incident.
- **The backlog HIGH rule was removed because it cannot work, not because it was inconvenient.** A queue is autocorrelated and mechanically seasonal (nothing ships over a shutdown, so backlog builds on its own). Measured: the seeded order surge A6 peaks at **z = 2.81**, while ordinary swings reach **4.09, 4.39 and 5.04**. No line admits the real one without admitting all of them. Backlog is watched and reported at WARN, and the policy says so, with the numbers and with what would fix it (level against throughput, or week-over-week at the same weekday).
- **Tuned on the first half, checked on the second.** The floors were chosen by looking at 2025-03-29 .. 2026-02-28 (A1–A3); the report carries the held-out window (A4–A6) separately, because a threshold picked to silence a particular false positive always looks good on the days it was picked from. **Held out: 2/2 found, precision 100%, zero false positives.**
- **Alternatives:** scoring flags rather than events (precision would read 2% on identical behaviour); counting only the top item per day (flatters the system by hiding everything it got wrong below the fold — reported separately as "brief precision" instead); tuning until the answer key looked perfect (the single remaining false positive is a genuine two-day lane dip the generator did not seed, and it is left in).
- **Reason:** plan §3.4 B13, week-7 definition of done. **Verified (`evals/REPLAY.md`, 22 tests):** over 535 days — **recall 100% (5/5), precision 80%, attribution top-1 100%, median lead time 1 day, decoy raised HIGH 0 times**, 5 HIGH events in 18 months of which 4 are the seeded anomalies. Of the 29 items a person would have been shown at six a day, 28 were real. Every target in the plan is met, and the report prints the failures as prominently as the totals.
