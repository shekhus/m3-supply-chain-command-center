# Design decisions — M3 Supply-Chain Command Center

One entry per decision that changes behaviour: what was decided, what else was considered, why, and the
evidence. Newest last. Project A's log is in `m3-trusted-data-foundation/docs/decisions.md`; decisions shared by
both repositories are recorded in whichever repo implements them and referenced from the other.

### B-001 · 2026-09-16 · Scaffold reuses Project A's proven infrastructure, with its own data model and ports

- **Decision:** the repository starts from the parts of `m3-trusted-data-foundation` that are already proven in CI and production, copied rather than imported: the numbered plain-SQL migration runner (`db/migrate.py`, advisory lock, checksums), settings loaded from the environment with a `.env` that wins over the shell, the server-side role dependency (`app/auth.py`), the lint runner, the repo-hygiene guard and its banned-term list, and the GitHub Actions workflow.
  - **What differs, deliberately:** schemas are `gold`, `metrics` and `ops` (no medallion bronze/silver: this system reads gold and never ingests); settings carry `GOLD_SOURCE` (standalone or external), `POLICY_FILE`, `JIRA_MODE` and console URL; the local stack publishes Postgres on **5433**, the API on **8010** and the console on **8511**, so it runs beside Project A without a port clash; the database is `m3cc`.
  - **Copied, not imported.** The two repositories stay independently runnable and deployable; a shared library would make Project B unable to start without Project A, which is exactly what B14 (standalone mode) exists to prevent.
  - The public plan and the addendum are the same files as in Project A, retitled: one governing document, two copies, no divergence.
- **Alternatives:** a shared internal package for the common infrastructure (couples the repos and complicates deployment for perhaps 300 lines); starting from scratch (re-solving migrations, config precedence and CI for no gain); reusing Project A's ports (the two stacks could not run side by side, and every demo needs both).
- **Reason:** CLAUDE.md's session ritual and the plan's week-6 definition of done. **Verified:** migrations create the three schemas, re-running is a no-op, an edited applied migration is refused, and a non-Postgres URL is rejected; lint is clean; the repo-hygiene guard scans every text file for engagement-identifying terms.

### B-002 · 2026-09-16 · Standalone gold from the same world as Project A, with a self-check that fails generation when a seeded anomaly is absent

- **Decision:** `make synth-gold` (`python -m synth.generate_gold`) builds gold here, so this repository runs and demos without Project A (plan B14).
  - **The same world, not a second one.** `synth/{config,world,events,gold}.py` are copies of Project A's generator modules, run with the same seed, so both repositories produce the identical population: same plants, customers, items, order lines, yield runs and inventory snapshots. `synth/anomaly_truth.py` keeps only the anomaly parts of A's `truth.py` (the window-versus-baseline check and the answer-key writer).
  - **Six seeded anomalies** carry over unchanged: A1 lane-level OTIF collapse (PLT-02 → C000031), A2 weight-basis fill-rate shortfall (PLT-01 CASE-READY, invisible on the count basis), A3 yield shortfall (PLT-03 L2 PRIMALS), A4 stalled lots ageing at DC-EAST, **A5 the holiday decoy** (a real dip that a day-of-week and holiday aware detector must not raise as HIGH), and A6 a backlog build-up at PLT-02.
  - **The self-check is a hard gate.** Each anomaly is recomputed at its own grain against a 56-day baseline, and generation writes nothing to `ground_truth/` and exits non-zero if an effect is missing or points the wrong way. Detection recall, precision, lead time and attribution accuracy are all scored against that file, so a ground truth that lies would invalidate every later measurement silently.
  - The generator also writes its pandas daily metrics to `data/metrics/`. They exist to support the self-check and to cross-check the SQL metric layer (B-3); the system itself reads `metrics.daily_*` in Postgres, never these files.
- **Alternatives:** importing Project A's `synth` package (B could then not run without A, which is exactly what standalone mode exists to prevent); writing a fresh world for B (the two projects would stop telling one story, and A's answer keys would no longer describe B's data); reading A's published gold only (no standalone demo, and B's evaluation would depend on A's pipeline being run first).
- **Reason:** plan §3.4 B14 and the week-6 definition of done. **Verified (`tests/test_generate_gold.py`):** the build is deterministic for a seed and differs for another; gold carries every column the metric layer needs; all six anomalies are measurably present, with the decoy a genuine −0.19 dip; the answer key and manifest are written with observed values and exactly one `expect_detection: false`; flattening the A1 series makes the self-check fail loudly; and **B's `fact_delivery` fingerprint equals Project A's row for row** when a sibling checkout is present. Live run: 51,571 delivery rows, 26,202 inventory snapshots, 6,175 yield runs, self-check passed for all six.


### B-003 · 2026-09-16 · Metric definitions live in numbered plain SQL, recomputed from raw fields and cross-checked against the generator

- **Decision:** every number this system will ever narrate is computed by `metrics/sql/*.sql` — plain, numbered, idempotent SQL run in order by `metrics/runner.py` (`make metrics`) into seven `metrics.daily_*` tables, one per grain a detector can work at: total, plant, lane (plant × customer), plant × product group, backlog by plant, yield line, and inventory location. No LLM, no Python arithmetic, no notebook. A metric changes by editing one file that a reviewer can read.
  - **The SQL recomputes on-time and in-full from the raw fields** (`010_delivery_flags.sql`) rather than trusting the flags published in gold, and a test asserts the two agree for all 51,571 rows. That proves this project implements the same definition rather than assuming it — the failure mode where two systems quote the same KPI and mean different things.
  - **Constants come from `policy.yaml`, never from the SQL.** `metrics.constants` is loaded from `policy.metrics` before every run (catch-weight tolerance 2%, at-risk window 5 days), because a `CREATE VIEW` cannot take a bind parameter and a tolerance hard-coded in three files is a tolerance that will one day disagree with itself. The same file carries the thresholds, seasonality (28-day baseline, the holiday list containing A5's week), allowed actions and limits that weeks 7–9 read.
  - **Each file merges by its own key**, so recomputing one day is idempotent and never duplicates a row; `metrics.runs` records the window, the per-table row counts and any error, which is the freshness the brief must disclose (principle 3).
  - **The generator's `_anomaly_id` marker column is deliberately NOT part of gold** and is dropped on load: it is answer-key material, and a detector able to read it would be scoring itself.
  - **Backlog is a continuous daily series** — a row per plant per calendar day, including days with no shipments — where the generator's pandas version emitted only days that had shipments. A queue of zero is a fact a detector needs; a missing row would silently break a consecutive-days rule.
- **Alternatives:** dbt (a second toolchain and a second definition language for eight models); computing metrics in pandas at request time (nothing to test independently, nothing to index, and the detectors would depend on a Python process rather than on data); trusting gold's published flags (faster, and it hides exactly the disagreement this project exists to catch).
- **Reason:** CLAUDE.md principle 1 and the week-6 definition of done. **Verified (`tests/test_metrics_sql.py`, 17 tests):** all seven SQL series equal the generator's independent pandas recomputation to 1e-9 on every shared key; the recomputed flags disagree with gold's published flags on 0 of 51,571 rows; A1's lane and A2's weight-basis shortfall are measurably present in SQL, with A2 still invisible on the count basis; rerunning a window leaves every table byte-identical; `gold.*` has no `_anomaly_id` column; a misnamed metric file and a policy missing a section are both refused. Live run: 561 / 1,677 / 15,638 / 8,229 / 1,692 / 6,175 / 940 rows over 2025-03-01 .. 2026-09-15.

### B-004 · 2026-09-16 · Three detectors in code, severity as the strongest verdict, and four gates that decide what is worth a morning

- **Decision:** anomalies are found by three independent detectors in `detect/`, all pure code, and no module under `detect/` may import an LLM — a test enforces it (principle 1).
  - **Baseline** (`baseline.py`): a 28-day rolling window, **de-seasonalised by weekday** before the z-score. Comparing a Monday against a mean containing four Sundays produces a signal about the calendar, not the business. Holidays are excluded from the window so a shutdown does not quietly lower the bar for the fortnight after it. A policy floor under the standard deviation stops a flat series producing an enormous z on its first ordinary wobble.
  - **Threshold** (`threshold.py`): the hard lines from `policy.yaml`, in three shapes — absolute level, absolute magnitude (yield variance is bad in both directions), and z relative to the segment's own history (400 open backlog lines is routine at one plant and alarming at another). Each fires only after its `consecutive_days`, and **a missing day breaks the run**: a metric that was not published is not evidence of a breach.
  - **CUSUM** (`cusum.py`): accumulates standardised deviations and fires at the policy's decision interval, catching a half-sigma drift that never trips the z detector on any single day — the shape of A2 and A4. It reports the **change point**, which is what lead time is measured from and what the brief says out loud.
  - **Severity is the strongest thing any detector said**, then capped by four gates: thin volume (a rate from three lines is arithmetic, not information), immaterial movement (a 1-point move on a 99% series is 6 sigma and nobody's morning), **no corroboration** (the baseline alone sees one day; HIGH needs consecutive days or an accumulated shift), and the **holiday allowance** — a day inside a holiday window is capped at WARN. The dip is still reported, never deleted.
  - **Detectors only speak in the direction that is bad for the metric.** OTIF at 100% is a good day; a detector that reports it teaches people to stop reading the brief.
  - **Ranking is dimensionless**: how many *material* moves it made (the policy's own `min_magnitude` is the unit), times how big the segment is next to a typical one at that grain. Ranking on magnitude × volume in native units means pounds always beat percentage points and the brief leads every morning with whichever metric has the largest unit — a fact about arithmetic, not about the business.
  - **Every grain an anomaly can live at is watched** (11 series over 173 segments): a lane collapse is invisible in the company total, and a weight-basis shortfall is invisible at plant level. That is the failure mode of the dashboard this project replaces.
  - **Some series are threshold-only, by design.** A line that runs four days a week has no 14 clean days in a 28-day window, so it gets no baseline and no `expected`. The brief must then cite the value against the policy line rather than invent an expectation.
- **Alternatives:** a single detector (each one misses a different shape — the cliff, the level, the drift); Prophet/ARIMA or an anomaly-detection library (a second dependency and an unexplainable number, where the whole point is that a VP can be told why something was flagged); an LLM asked "is this unusual?" (principle 1, and unreproducible); ranking by raw magnitude (see above).
- **Reason:** plan §3.4 B2, week-7 definition of done. **Verified (41 tests):** hand-computed z on a paper series; an ordinary Sunday unremarkable with the weekday adjustment and flagged without it; a holiday collapse never entering the mean; the consecutive-day rule refusing to bridge a missing day; CUSUM catching a drift whose every day is below z=3, staying silent on a wobble, and ignoring the 4 July week; each gate capping in isolation; and against the answer key — **A1, A2, A3, A4 and A6 all reach HIGH inside their windows, lead times 0/0/1/4/7 days, and A5 is reported but capped at WARN, where the same detectors with `known_holidays` emptied raise it HIGH.** Over the full 535-day window: 9,265 findings, 1,793 at WARN or above, 932 HIGH (1.7 a day). Precision and recall against the answer key are scored in B-6, and the floors will be tuned there with measured numbers rather than guessed at here.

### B-005 · 2026-09-16 · Attribution by exact rate/mix decomposition, ranked by who got worse

- **Decision:** `detect/attribute.py` decomposes an anomaly's movement into the finer segments underneath it, in code. A rate at a coarse grain is a weighted average of the same rate at a finer one, and the movement between two windows splits exactly:
  - `R₁ − R₀ = Σᵢ wᵢ₁(rᵢ₁ − rᵢ₀)` — the **rate effect**: this segment got worse — `+ Σᵢ rᵢ₀(wᵢ₁ − wᵢ₀)` — the **mix effect**: this segment is a larger share of the volume. The identity is exact, so the contributions sum to the movement being explained. That closure is what licenses printing a percentage at all.
  - **Drivers are ranked by the rate effect, not by the total.** Measured: ranking on the sum made PRIMALS the top driver of A2's shortfall (a volume-mix artefact) and hid CASE-READY, the seeded cause. A short window's volume mix wanders against a 28-day baseline, and those terms are large enough to bury the segment that actually deteriorated. Ranked on the rate effect, the top driver is the seeded segment in every case tested.
  - **The publishable number is `rate_effect_pct`** — the segment's share of the performance change — because a share of the *whole* movement can exceed 100% or flip sign when the mix moved the other way. "PLT-02 accounts for −52% of the drop" is arithmetically true and unpublishable.
  - **When the mix half dominates, the attribution says so** instead of naming a culprit: "the movement is mostly a change in what was shipped, not in how any segment performed". Those are different problems with different owners.
  - **Holidays are excluded, and evidence refs name only days that entered the arithmetic.** A window lying entirely inside a shutdown attributes nothing — naming a driver there would be blaming a lane for a day the plants were shut, which is the A5 mistake wearing a different hat.
  - **An anomaly already at the finest grain held says so** rather than inventing a driver. Backlog and inventory have no finer table, and the honest output is "this is as fine as the data goes".
- **Alternatives:** a single "top segment by absolute change" (ignores volume, so the smallest lane always wins); Shapley values over segments (defensible, far slower, and nobody in the room can check the number); asking the LLM which segment mattered (principle 1 — and it would be a guess dressed as a finding).
- **Reason:** plan §3.4 B3, week-7 definition of done. **Verified (15 tests):** a hand-computed two-lane decomposition (0.90 → 0.70 on half the volume = −0.10, all of it that lane's, zero mix); a pure mix shift where nobody performed differently, correctly labelled and not blamed on anyone; contributions summing to the total movement across four lanes with both rates and volumes moving; a deteriorating lane outranking a steady one with a bigger mix term; a segment appearing in only one window credited the parent's rate so it is never blamed; and against the answer key — **from the plant-level anomaly, the top driver is the seeded lane C000031 (40.4% of the performance change); from the company total it is PLT-02; from PLT-01's fill-rate anomaly it is CASE-READY**, the group whose shortfall is invisible on the count basis. `make detect` now prints the drivers under each incident.

### B-006 · 2026-09-16 · Replay scoring, and what the first measurement said about the thresholds

- **Decision:** `make replay` walks the history day by day with no LLM, merges flags into events, and scores them against `ground_truth/anomalies.json` into a generated `evals/REPLAY.md`. The scoring definitions are written down before the code, because each one can be chosen to flatter the result:
  - **An event, not a flag.** A three-week collapse produces twenty-one flags; counting them separately would make recall effortless and precision catastrophic, and neither number would describe what a person experiences. Runs are merged, bridging gaps of up to three days.
  - **A match needs a shared segment key.** An event at a coarser grain matches — a plant-level drop is the lane collapse seen from further away — but a company-total wobble sharing no key with the seeded segment does not, or every anomaly would be "detected" by a company-level twitch.
  - **Recall at WARN or above, precision at HIGH.** Recall asks whether the system noticed; precision asks whether it interrupted someone.
  - **Lead time is measured from the anomaly's start and never goes negative.** An event already running when the anomaly began belongs to whatever came before it; crediting it would report prescience.
  - **The decoy is scored on its own days.** An event beginning a week earlier that runs into the holiday was raised for its own reasons.
- **What the first run said, and what changed because of it.** The first replay scored **recall 100%, precision 2%** — 383 HIGH events, 377 of them with nothing behind them. Four things were wrong, and all four are worth more than the number they fixed:
  1. **The thresholds in `policy.yaml` were guesses, and the data said so.** OTIF's `high` of 0.90 sits at the measured median of 0.905 — the rule fired on half of all days. `lb_at_risk_within_5d`'s warn of 1,000 sat below its median of 1,410. Every level is now set from the observed distribution (warn ≈ the worst 5% of days, high ≈ the worst 2%), and the percentile is written in the file next to it.
  2. **A line drawn for the company is not the line for one lane.** `threshold_overrides` scopes a rule by grain. A lane's *daily* rate is 0 or 1 — median 1.00, tenth percentile 0.00 — so no absolute line means anything there; a lane is judged on its **seven-day volume-weighted rate against its own 28-day norm**, compared like with like, which is the number an operations lead would use.
  3. **An incident is a policy breach, not a statistical shift.** The baseline and CUSUM detectors can raise WARN on their own — something moved, someone should look — but only a line in `policy.yaml` makes it HIGH. Without this rule the statistical detectors produced 322 of 365 HIGH flags, nearly all of them real movements nobody needed waking for. Statistics say a thing changed; policy says it matters.
  4. **CUSUM never reset after signalling** — a genuine bug against the textbook procedure, which left the statistic above the decision interval for as long as a shift lasted and reported the same change every day for a fortnight.
  - Also: **a holiday cannot extend a breach run.** A four-day shutdown was handing the consecutive-day rules their days for free, so the first trading day afterwards — backlog still clearing — became an incident.
- **The backlog HIGH rule was removed because it cannot work, not because it was inconvenient.** A queue is autocorrelated and mechanically seasonal (nothing ships over a shutdown, so backlog builds on its own). Measured: the seeded order surge A6 peaks at **z = 2.81**, while ordinary swings reach **4.09, 4.39 and 5.04**. No line admits the real one without admitting all of them. Backlog is watched and reported at WARN, and the policy says so, with the numbers and with what would fix it (level against throughput, or week-over-week at the same weekday).
- **Tuned on the first half, checked on the second.** The floors were chosen by looking at 2025-03-29 .. 2026-02-28 (A1–A3); the report carries the held-out window (A4–A6) separately, because a threshold picked to silence a particular false positive always looks good on the days it was picked from. **Held out: 2/2 found, precision 100%, zero false positives.**
- **Alternatives:** scoring flags rather than events (precision would read 2% on identical behaviour); counting only the top item per day (flatters the system by hiding everything it got wrong below the fold — reported separately as "brief precision" instead); tuning until the answer key looked perfect (the single remaining false positive is a genuine two-day lane dip the generator did not seed, and it is left in).
- **Reason:** plan §3.4 B13, week-7 definition of done. **Verified (`evals/REPLAY.md`, 22 tests):** over 535 days — **recall 100% (5/5), precision 80%, attribution top-1 100%, median lead time 1 day, decoy raised HIGH 0 times**, 5 HIGH events in 18 months of which 4 are the seeded anomalies. Of the 29 items a person would have been shown at six a day, 28 were real. Every target in the plan is met, and the report prints the failures as prominently as the totals.

### B-007 · 2026-09-16 · The evidence pack is the whole world the model gets, and the permission filter is part of building it

- **Decision:** `pack/` builds one JSON per run — metrics, anomalies, drivers, detector reasons, freshness, windows — and it is the only thing any model is ever shown. Three properties make the week-8 validator possible at all:
  - **Every quotable number is a named fact.** `facts` is a *flat* map from a ref (`I1.value`, `I1.driver1.share`, `freshness.delivery.days`) to the number, its unit and its label. Flat, not nested: a validator resolving `I1.drivers.0.share` through a tree is a validator with bugs in it.
  - **Rounding happens once, in code.** Each fact carries the exact string to use — `74.1%`, not `0.74138`. A model asked to render a rate as a percentage will sometimes write 74%, sometimes 74.14%, and occasionally 74.8%, and the last one is indistinguishable from the others inside a paragraph of confident prose. The narration copies a string; it never formats a number.
  - **Nothing else is in scope.** No metrics tables, no rankings arithmetic, no history to average — the context series is held on the item and deliberately excluded from `for_prompt()`. If a number is not a fact in the pack, there is no way to say it and pass the validator.
  - **Two units that both read as "points".** `points` is a number already in percentage points (yield variance); `rate_change` is the difference between two rates and must be multiplied out first. Keeping them apart is the difference between "0.5 points" and "50.0 points" — the first version of `_display` got this wrong for yield.
  - **A holiday is named before the numbers are.** The pack carries a `calendar_note` when the run date falls in a holiday window, because otherwise the 4 July brief opens with OTIF at 34.6% and no explanation, and the reader either panics or learns to ignore the brief every July.
  - **An empty brief says which kind of empty it is**: nothing moved, nothing was material, or nothing happened *that you can see*. Rendering all three as silence teaches the reader that silence means nothing in particular.
- **The permission filter is a parameter of building the pack, never a step after it (B-8).** `build_pack(..., audience)` narrows before detection results are turned into items, so another plant's numbers are *absent from the pack* — and therefore from the prompt, the model's context and the logs — rather than hidden by a renderer. A test asserts that `PLT-02` and `C000031` do not appear anywhere in a PLT-01 manager's serialised prompt.
  - **A segment with no plant belongs to nobody in particular.** Company totals and distribution centres are visible only to an unrestricted audience: showing a plant manager a company number they can neither act on nor check is the wrong kind of transparency.
  - **An unknown user is refused, not defaulted.** Defaulting to "a plant manager for no plants" produces an empty brief, which looks like a quiet morning — the failure that hides itself.
  - **Roles are data.** Adding one is a row in the directory, never an `if role == ...` in a renderer.
- **Alternatives:** passing the raw metrics rows to the model and asking for prose (principle 1, and unverifiable); nesting facts inside items (a harder validator for no gain); filtering on display (leaves the data in the prompt and one bug away from the reader); letting the model format numbers (see the rounding note).
- **Reason:** plan §3.4 B4 and B5, week-8 definition of done. **Verified (17 tests):** every ref an item carries resolves to a fact; display strings match their values for every unit; a rate change reads in points while a yield variance is not multiplied; the prompt view contains no number that is not a fact and no ranking internals; A1 arrives with `C000031` as its named driver and a cited share; freshness is disclosed even when nothing is stale; the 4 July pack carries its calendar note and contains no incident; a quiet day distinguishes "immaterial" from "not yours"; and a PLT-01 manager's prompt contains no trace of PLT-02.

### B-008 · 2026-09-17 · Grounded narration: a contract the model cannot break, a validator it cannot argue with, and a brief that always ships

- **Decision:** `narrate/` turns a pack into a brief through four pieces — a contract, a prompt, a validator and a fallback — with `llm/client.py` copied from Project A, where it has been carrying real traffic.
  - **A claim cannot exist without a citation.** `metric_ref` is a required field, so "the model forgot to cite" is not a failure mode to catch; it is a shape the model cannot return. Citation coverage is therefore structurally 100%, and the validator's real job is the harder one: **a claim that cites a real fact and then says a different number** — wrong, cited and completely convincing.
  - **The validator checks against the pack, never by asking the model whether it was careful.** Unknown ref, number not among the facts cited beside it, severity changed, a segment the pack never mentioned, a stale source not disclosed. Its complaints are the retry prompt: "you wrote 74.8%, the fact says 74.1%" is a far better instruction than "try again".
  - **One correction, then the template.** Past two attempts the honest options are a flatter brief that is certainly right or an argument with a language model at six in the morning. The templated brief is validated like any other — a test asserts it can never fail the gate — and `fallback_reason` is recorded, because a fallback rate nobody publishes quietly becomes 100%.
  - **The model may quote the pack's own sentences.** `why_flagged` ("20.0 points below its own normal for 2 days running") is rendered in code from the detector's output; a brief forbidden from repeating why something was flagged cannot explain anything. Those numbers are quoted rather than cited, and must appear verbatim in a string the pack supplied.
- **What the first live sample changed.** Twenty briefs against `openai/gpt-oss-120b`: citation coverage 100%, but **first-pass validity 35% and a 25% fallback rate**. Four causes, and only one was the model's:
  1. **Names with typographic hyphens.** The model writes `PLT‑02` with U+2011; a validator comparing bytes sees a bare "02" and rejects the sentence. Three of four fallbacks in the second run were this. Text is now normalised — dashes, non-breaking spaces, the minus sign — before any comparison, and the names masked out are **taken from the pack** rather than guessed at by regex, which is what the first version did.
  2. **A change written without its sign.** "OTIF fell by 9.4 points" is how a person writes −9.4. Rejecting it was a validator enforcing notation rather than truth; the magnitude must still match, and the direction is carried by the sentence and the item's own `direction`.
  3. **A union type in the strict schema.** `{"type": ["string", "null"]}` is rejected outright by strict mode on this provider, costing a brief that fell back for a reason unrelated to its writing. `freshness_line` is a plain string, empty when there is nothing to disclose.
  4. **`max_tokens` too low.** A six-item brief with a claim per number runs past 4,000 output tokens and comes back truncated. Raised to 8,000.
  - The sample also found a bug in the *pack*: `VOLUME_LABELS` was keyed by metric, but the column a grain carries depends on the grain — a plant × product-group fill rate is weighted by lines, and the pack was calling those "ordered pounds". A wrong label on a right number survives every numeric check and misleads the reader anyway. Now keyed by the grain's own volume column.
  - And a gap in the eval itself: rejected drafts were thrown away, so a failure could only be guessed at. They are kept now.
- **After those fixes, the same twenty days: citation coverage 100%, first-pass validity 100%, fallback rate 0%, $0.0017 per brief.** The corrections were to the checker and the plumbing, not to the standard — the adversarial tests (right citation with a wrong number, invented ref, talked-up severity, invented plant, stale day narrated over) all still fail the brief.
- **Alternatives:** asking the model to double-check its own numbers (unverifiable, and a model that miscounts will re-miscount); regex-free trust in strict-schema output (a schema cannot express "this number equals that fact"); three or more retries (cost and latency for a diminishing return, and it hides the fallback rate); no fallback (a missing brief is a silent failure — nobody notices nothing arrived until the week somebody needed it).
- **Reason:** plan §3.4 B6, week-8 definition of done. **Verified (30 tests + `evals/NARRATION.md`):** the templated brief passes the gate on 120 packs across 60 days and two audiences; a right citation with a wrong number, an invented ref, an invented item, a talked-up severity, an invented plant and an undisclosed stale source are each caught; a non-breaking hyphen, an unsigned change and a quoted detector sentence are each accepted; masking a name does not let a wrong number through beside it; the model path is exercised with a stub for "wrong twice", "invalid JSON twice" and "provider outage", each landing on the template with a reason recorded.

### B-009 · 2026-09-17 · Actions drafted in code, and a policy gate that judges them whoever wrote them

- **Decision:** `act/` proposes actions and refuses the ones policy does not allow. Nothing in the module executes anything, and nothing reaches `APPROVED` without a person (principle 5).
  - **Bodies are assembled from the pack's facts, in code, not written by the model.** A ticket is a durable artefact somebody reads next month without the brief beside it, and a paraphrased number in a ticket is a wrong number with a long life. Every figure appears with the ref it came from, so the ticket says where to check it.
  - **The type comes from `policy.yaml`, and severity only decides how loudly.** A HIGH item takes the policy's first allowed action; a WARN takes the least intrusive one the policy lists for it. Nobody wants a ticket for every WARN, and nobody wants a HIGH arriving as a note somebody reads on Thursday. Both lists are the business's to change.
  - **The gate runs on every action regardless of origin** — the drafter, a future model, a console retry, a test. A drafter that can only produce allowed actions is one refactor away from producing a disallowed one; the gate is what will still be true afterwards. Four rules: the type must be allowed for that anomaly type, the brief's cap holds, no duplicate of something already open within the policy's window, and the same brief never proposes the same problem twice.
  - **A blocked action is kept with its reason, not dropped.** The console can then show what the system wanted to do and was refused, which is how policy drift becomes visible instead of silent.
  - **Approval is bound by the same policy.** `check_decision` re-checks the allow-list at the moment of approval, because otherwise an editor who changes an action's type — or a direct API call — walks straight past it. Approving means "yes, do the thing policy permits", not "yes, do anything". Rejecting is always allowed, including for something policy would never have permitted.
  - **A typo in the allow-list is an error, not a refusal.** `jira_tickets` instead of `jira_ticket` raises, rather than quietly blocking every ticket the business expected to see.
- **Alternatives:** letting the model choose action types (it would be choosing what the business permits, and the gate would be the only thing standing between a prompt and a ticket); dropping blocked actions silently (hides the drift); enforcing the allow-list only in the console (an API call bypasses it); no duplicate suppression (the same lane raises a ticket every morning until somebody mutes the system entirely).
- **Reason:** plan §3.4 B7 and B8, week-9 definition of done. **Verified (27 tests):** a ticket carries every number with its ref, the detector's own reason, the driver segment and a stale-data caveat; `update_m3` smuggled in as a type is blocked before anyone is asked and recorded as a violation; an unknown anomaly type, an action about an item not in the brief, a duplicate of an open ticket, a second copy within one brief and anything past the cap are each refused with a reason; an old or rejected ticket does not suppress a new one; approving a blocked action or an edited-to-disallowed type raises; and no path through the gate produces an `APPROVED` action.

### B-010 · 2026-09-17 · A checkpointed approval graph, stopped before it can touch anything

- **Decision:** the run is a LangGraph state machine — `build_pack → narrate → draft_actions → policy_gate → ⟪interrupt⟫ → execute → record` — compiled with `interrupt_before=["execute"]` and a Postgres checkpointer on its own `graph_checkpoints` schema.
  - **Why a graph here and plain code in Project A.** A's pipeline is fixed (profile, map, validate, publish) and a function call expresses it perfectly. This one has a pause in the middle that must survive a process ending: the brief goes out at 06:00 and somebody approves at 14:00, from a different machine. Writing that by hand means writing serialisation, resumption and a step ledger — which is what LangGraph already is. Smallest abstraction that fits, in both directions.
  - **The interrupt is a stop, not a flag.** The graph cannot *reach* the node that touches the outside world without a person resuming it; `execute` is not asked to check whether approval happened. The test throws away the compiled graph, the saver and the connection, then resumes from a fresh set — because a pause that only works inside one process is not the property being claimed.
  - **State is plain JSON.** Packs, briefs and actions are dumped on the way in and rebuilt on the way out; a checkpoint another process cannot read is not a checkpoint.
  - **The checkpointer's tables are the paused machine; `ops.*` is the archive.** Briefs, actions and decisions are recorded as the durable business record, separately, so they outlive any change to the graph's internals or LangGraph's own schema.
  - **One thread per day per reader.** A cron firing twice resumes the same run rather than producing a second brief, and each audience's brief is its own thread — which is also what keeps one reader's approval out of another's run.
  - **Policy is re-checked at the moment of approval**, inside `execute`, because resuming is another way in: a tampered state or a direct call must not walk past the allow-list. Two layers refuse a bad action — the contract cannot even parse an invented type, and the gate refuses a real type the policy does not permit for that anomaly.
  - **Narration's retry stays inside the narrate node** rather than becoming a graph edge that loops back to the model. The plan's diagram shows `validate` as its own node; keeping the loop where the call is means one implementation of "one correction, then the template" rather than the same policy spread across two places, and the validation result travels in state either way. This is a deliberate deviation from the diagram.
- **Alternatives:** a boolean `approved` column and a cron that executes it (no resumable state, no step ledger, and the execute path is reachable by any code that sets the flag); Temporal or Airflow (heavier than one pause needs); putting the checkpoint tables in `ops` (couples a vendor's schema to the business record).
- **Reason:** plan §3.4 B9, week-9 definition of done. **Verified (14 tests):** a run pauses with `execute` as its next node and nothing reaches the tracker; **the pause survives the process that created it** — started, discarded, resumed from Postgres by a new saver, and executed; a rejection never executes; an edit is what the tracker receives, not the drafter's wording; an action nobody decided is left alone (silence is not consent); a retryable failure leaves the action open for the next run; a quiet day needs no approval; a second run for the same morning resumes rather than duplicating; loading a run to display it does not advance it; each audience gets its own thread and a plant manager's actions carry no other plant; and the checkpoint tables live only in `graph_checkpoints`.

### B-011 · 2026-09-17 · The adapter that leaves the building, and the record that outlives the run

- **Decision:** `act/jira_adapter.py` executes an approved action; `act/store.py` writes what happened; `service.py` is the only module that knows Postgres, Groq and Jira all exist.
  - **A failure at the tracker is never an exception in somebody's face.** The person approved at 14:00 and walked away. A timeout or a 5xx becomes `FAILED_RETRYABLE` — the action stays open, the console shows it, the next run tries again. A 4xx becomes `FAILED`, because retrying a wrong request forever is how a queue fills with identical failures. Even an unexpected bug in the adapter returns `FAILED_RETRYABLE` rather than losing the approval.
  - **The mock is a tracker, not a stub.** `JIRA_MODE=mock` writes to `ops.mock_jira` through the same code path the live adapter uses; only the `Tracker` behind the seam differs. A demo points at real rows.
  - **Live mode refuses to start without its credentials.** An adapter that silently falls back to the mock when a variable is missing is the worst of both: the demo looks real and nothing was ever created.
  - **`ops.mock_jira.action_id` is deliberately not a foreign key.** It stands in for a system outside this database, and a real tracker has no referential integrity with our rows — it accepts a ticket whether or not we have finished writing our record. Modelling it with a foreign key made the mock fail in a way the live adapter never could, which is how the mistake was found.
  - **The record is written at the pause, not only at the end.** A brief waiting for approval has already proposed things, and tomorrow's duplicate suppression has to see them; a run that persists itself only after approval is invisible for exactly as long as it is waiting.
  - **Decisions are stored separately from the action.** An action row is updated as it moves; a decision row never is. "Who approved this, and what did they change?" has to survive what happened next.
  - **Suppression reads the database.** A gate consulting an in-memory list suppresses nothing in production: the ticket it needs to know about was raised four days ago by a different process.
- **Alternatives:** raising the tracker's exception to the caller (the caller is a cron at 06:00 and a person who has gone home); retrying inside the adapter (hides the failure rate and turns one outage into a thundering herd); one `actions` table holding the latest decision inline (loses the audit trail on the next update); the mock skipping the write entirely (then the demo has nothing to show and the path is untested).
- **Reason:** plan §3.4 B10, week-9 definition of done. **Verified (21 tests + an end-to-end run):** a timeout, a refusal and an adapter bug each produce the right status and are recorded on `ops.tool_calls`; the live adapter returns its key, treats 5xx as retryable and 4xx as refused, and calls an accepted issue with no key a refusal; live mode without credentials refuses to start; the mock's keys do not collide. **End to end on a fresh database:** a brief pauses with three proposals, one approval creates `SC-0001`, `ops.runs`/`actions`/`decisions` all carry it, and the next day's run suppresses the same problem with the ticket key in the reason.

### B-012 · 2026-09-17 · The API decides who sees what; the console only asks

- **Decision:** three endpoints — `POST /brief/run` (what the cron calls), `GET /brief/{thread_id}` (read a paused run) and `POST /brief/{thread_id}/decide` (the only way past the interrupt) — with a Streamlit console that talks to them over HTTP.
  - **The audience comes from the API key, never from the request.** `API_AUDIENCES` maps a key to the reader it belongs to, so a plant manager's key returns a plant manager's brief whatever the URL asks for. A request that could name its own audience would make the permission filter in `pack/permissions.py` decorative, and a filter nobody can bypass is the only kind worth having.
  - **A key may only touch its own threads.** Knowing the date is not permission: `GET /brief/2025-09-15:vp` with a plant key is a 403, not a brief. Without that check, the whole pack-filtering story would collapse to security by obscure URL.
  - **Building, reading and deciding are separated by role.** An analyst may build, a viewer may read, only an owner may decide. Reading never advances a run.
  - **The console holds no permissions of its own.** It talks to the API rather than the database, because a console with its own connection would be a second place for the permission filter, the policy gate and the interrupt to be wrong — and the one people actually use. Its errors are in words: a rejected key, a forbidden brief and an unreachable API each say what to do.
  - **The console shows what policy refused**, not just what it proposed, so a gate that has drifted from what the business needs is visible in the place people look every morning.
  - **`METRICS_SOURCE` chooses Postgres or parquet.** A deployment reads the tables `make metrics` filled; the standalone demo reads what the generator wrote. This is a deployment knob the README needs, and it is also what lets an API test run against a fresh database.
- **Alternatives:** an `audience` query parameter (anybody can edit it); the console reading Postgres directly (faster to write, and it duplicates every rule that matters); one role for everything (an analyst who can build a brief can then approve a ticket); returning 404 instead of 403 for another audience's thread (hides the boundary, and makes "does this exist?" the probe).
- **Reason:** plan §3.4 B9 and the console row of week 9, week-9 definition of done. **Verified (14 tests):** a brief is built and waits; a PLT-01 key's brief contains no PLT-02 numbers and has its own thread; one key reading another's thread is refused with the reason; reading does not advance a run; a viewer cannot build and neither a viewer nor an analyst can decide; approving executes and returns the ticket reference with the decider recorded; an edit is what reaches the tracker; rejecting executes nothing; an unknown or missing key gets 401; an unbuilt thread is 404; and a second run for the same morning returns the same brief.

### B-013 · 2026-09-17 · Delivery is a notification, and a failed send never loses the brief

- **Decision:** `deliver/` renders the validated brief as an email or a Slack message and sends it; `scripts/morning.py` is what a scheduler calls.
  - **Rendering is copying.** Every sentence in the message already exists in the brief that passed the citation gate. A renderer that summarises becomes a second writer whose output nothing checked — and it would be the version most people actually read.
  - **The message links to the console; it never invites approval by reply.** Approving happens where the evidence is. A mail that could be approved by replying is a mail that gets approved without anybody seeing what they approved.
  - **Recipients are configured per audience.** A brief filtered for one plant, then emailed to a global list, would undo the permission filter at the last possible step and in the medium most likely to be forwarded. An audience with nobody configured gets nothing, rather than falling back to everybody.
  - **Delivery is the last thing that happens and the least important.** The brief is written, validated and recorded first, so every failure here is caught, recorded on `ops.tool_calls` and returned as a result — never raised into the run. A missing brief is a silent failure; a missing email is a noisy inconvenience, and the console still has it.
  - **The cron runs in-process rather than posting to its own API.** A cron that authenticates to its own service needs a key in a second place, and the HTTP hop's only contribution would be another way to be down. One audience failing does not stop the others; the exit code reports whether any brief failed to *build*, not whether one failed to send.
- **Alternatives:** an HTML-only email (unreadable in half the clients that matter and useless on a phone); approving by reply (see above); one global recipient list (undoes B-8 in one line); raising delivery failures (turns somebody else's mail server into this system's outage); a scheduler hitting `POST /brief/run` (a second copy of the key, for nothing).
- **Reason:** plan §3.4 B11, week-9 definition of done. **Verified (16 tests + a live run):** the text contains every headline, explanation, claim and ref from the brief and nothing else; the console link is present and the word "reply" is not; a stale brief says so in its opening lines; Slack is capped at five items with the rest behind the link; recipients resolve per audience and an unconfigured audience is skipped rather than guessed; missing SMTP configuration, an unreachable mail server, a missing webhook, a Slack rejection and an unknown channel each produce a recorded result instead of an exception. **Live:** `scripts/morning.py --date 2025-09-15` built the VP brief (3 items, narrated by the model) and the PLT-01 brief (empty — nothing for that plant), reported the email failure and the skipped webhook, and exited without losing either brief.

### B-014 · 2026-09-17 · Observability, the eight failure cases, and one report that generates itself

- **Decision:** three pieces landed together because each is only worth having if the others are true.
  - **Ops questions are answered in SQL views** (`ops.v_run_health`, `v_model_usage`, `v_narration_health`, `v_pending_approvals`, `v_action_failures`, `v_policy_refusals`, `v_delivery`), not in a Streamlit page. The number an operator reads at 08:00, the number a test asserts and the number the RUNBOOK quotes are then the same number, rather than three pandas expressions somebody rewrote.
  - **`/ops/summary` names its alerts after RUNBOOK sections** — `no-briefs`, `narration-falling-back`, `approvals-piling-up`, `action-failed`, `action-retrying`. An alert without a page is a pager without an answer. The four things that can be wrong and are invisible from a brief: nothing ran, the model stopped being usable, approvals are piling up, actions are failing at the tracker.
  - **The ops page lives in the same console as the brief.** An operations page nobody opens is wrong for a month before anybody notices; this one is one click from where approvals happen.
  - **The plan's eight failure cases are their own suite**, one test per row, named after the failure, with the expected behaviour in the docstring — the place to send a sceptical reader. Plus two that underwrite the rest: the brief always ships whatever the model does, and no module outside tests contains anything resembling a write to the ERP (principle 8, checked rather than asserted in prose).
  - **`make eval` generates `evals/REPORT.md`** from four sections — detection, narration, the policy gate under adversarial input, and the failure cases run as a subprocess so the report cannot claim what the tests do not. A number in a report that nobody can reproduce with one command is marketing.
