# Demo script

Twelve minutes, no slides. The point is not that it works — everything in a portfolio works — it is that
every number is checkable and every claim has something behind it that you can be asked about.

Set up before you start: `make up && make migrate && make metrics`, console at `localhost:8511`, a terminal in
the repo, and `evals/REPORT.md` open in a tab.

---

## 0 · The one sentence (30 seconds)

> "Every morning this answers three questions — what changed, why it matters, what to do about it. Code
> computes every number, the model only writes the explanation, and nothing happens until a person approves."

## 1 · The problem, in the data (90 seconds)

Open a terminal:

```
python scripts/run_detect.py --parquet --date 2025-09-15
```

> "One customer's lane at PLT-02 is at 50% OTIF against a normal of 87.5%. Here is the thing that makes this
> hard: the company total that day never moves outside its own noise. If you are watching the number everybody
> watches, this is invisible. There is a test asserting exactly that — the dashboard failure this project
> exists to answer."

Point at the second line: the plant-level drop, with the lane named as 40% of the change.

> "That 40% is not a phrase the model chose. It is a decomposition: how much of the plant's movement each lane
> accounts for, computed in code, and it is the number the brief will cite."

## 2 · The brief (2 minutes)

In the console: **Build the brief** for 2025-09-15.

Read the summary out loud, then open **The numbers behind it** on the first item.

> "Every sentence with a number in it carries a reference — `I1.value`, `I2.driver1.share`. Those are not
> decorations. A validator resolves every one against the evidence pack before this page renders, and a brief
> with a number that does not match its citation never ships."

Then, the part worth pausing on:

> "The model is given the pack and nothing else. Not the tables, not the history — it cannot average anything
> because it never receives anything to average. And the numbers arrive pre-rounded: it is asked to copy
> `74.1%`, not to turn 0.74138 into a percentage. That is where a grounded number quietly becomes a wrong one."

## 3 · The approval (2 minutes)

Scroll to **What to do about it**. Edit the title of the first action, then **Approve with my edits**.

> "Three things just happened. The tracker received my words, not the drafter's. The policy gate re-checked
> the action at the moment of approval, because approving means 'do the thing policy permits', not 'do
> anything'. And a ticket exists — `SC-0001` — in the mock tracker."

Show it:

```
psql $DATABASE_URL -c "select key, summary from ops.mock_jira order by created_at desc limit 3"
```

Then the part people do not expect:

> "The run was *paused* in Postgres between the brief being built and this approval. I could have restarted the
> process, or approved from a different machine tomorrow, and it would have resumed from exactly here. That is
> the only reason there is a graph in this project rather than plain code — and there is a test that throws the
> whole process away between the pause and the approval."

## 4 · The refusals (2 minutes)

> "The interesting part of a system like this is what it refuses to do."

**The holiday.** Build the brief for `2026-07-04`.

> "OTIF is at 34.6%. Every naive detector raises that as a crisis. This one says, first line, that it is a
> shutdown in the policy calendar — and caps it at WARN so nobody is woken. The world has that dip seeded as a
> deliberate decoy, and there is a test that the same detectors with the holiday list emptied *do* raise it.
> That is what makes it a test rather than a claim."

**The policy gate.** From `evals/REPORT.md`, the adversarial table.

> "Four kinds of action nothing here can produce, tried against the gate anyway — a type policy does not list,
> a type not allowed for this anomaly, an anomaly type it has never heard of, an action about an item not in
> the brief. All blocked before a person is asked, and recorded as violations. A drafter that can only produce
> allowed actions is one refactor away from producing a disallowed one."

**The permission filter.** If there is time:

```
curl -s -H "X-API-Key: $PLANT_KEY" "$API/brief/run?run_date=2025-09-15" | grep -c PLT-02
```

> "Zero. Not hidden in the UI — absent from the pack, so absent from the prompt, so the model could not mention
> it if it tried."

## 5 · The measurements (2 minutes)

`evals/REPORT.md`, generated by `make eval`.

> "Recall 100%, precision 80%, attribution 100%, the decoy never raised, citation coverage 100% across 652
> numbers in twenty real briefs, $0.0019 each."

Then, deliberately:

> "Two honest caveats, both in the report. Precision counts every HIGH with no seeded anomaly behind it as
> wrong, and the generator promises nothing about the other 529 days — so that 80% is a floor. And the
> thresholds were tuned on the first half of the history, so the report scores the held-out half separately.
> It comes out at 100%."

And the one to volunteer:

> "The first replay scored 2% precision. Four things were wrong, and only one was the model's: thresholds that
> were guesses — OTIF's 'high' line sat at the median, so it fired on half of all days — rules written for the
> company applied unchanged to a single lane, no separation between 'statistics noticed' and 'policy says this
> matters', and a CUSUM that never reset after signalling. That is in the decisions log with the numbers."

## 6 · What it will not do (90 seconds)

> "Backlog has no HIGH rule. The measurement showed a z-score cannot separate the seeded surge — z of 2.81 —
> from ordinary swings that reach 5.04. Any line that admits the real one admits all of them. So I removed the
> rule and wrote down what would fix it, rather than tuning it until the answer key looked good."

> "And nothing here writes to M3. The destinations are a ticket and a note. That is a decision, not a
> limitation."

## 7 · Close (30 seconds)

> "One foundation, two uses. The other repository governs the data and proves the numbers are trustworthy;
> this one acts on them and proves every claim is traceable. Both are honest about what they cannot do — the
> decisions log has the failures as prominently as the results."

---

## If they ask

**"Why LangGraph here and not in the other project?"** A's pipeline is fixed — profile, map, validate, publish
— and a function call expresses that. This one has a pause that must survive a restart. Smallest abstraction
that fits, in both directions.

**"How do you know the model isn't making numbers up?"** It cannot say a number that is not a fact in the pack
and pass the validator. And the validator is tested with briefs built to get past it: the right citation with
the wrong number, an invented reference, a severity talked up.

**"What happens when the model is down?"** The templated brief ships, validated the same way, and the fallback
rate is on the ops page — because a fallback rate nobody publishes quietly becomes 100%.

**"What would you do with two more weeks?"** The backlog measure, alert routing, and detector drift monitoring
— in that order.
