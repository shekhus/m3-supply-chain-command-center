### 1.3 The synthetic data generator (`synth/`) — shared design, two instances

This is the most important shared component. Its quality determines whether your evaluations mean anything, because **the generator knows the truth** and writes it to `ground_truth/`.

**Fictional world:** Prairie Bend Foods. 3 plants (PLT-01, PLT-02, PLT-03), 2 distribution warehouses, ~30 customers (retail, foodservice, distributor), ~80 items in product groups (ground, primals, case-ready, value-added, offal), catch-weight items flagged. 18 months of daily data (Mar 2025 – Aug 2026). Deterministic seed.

**Tables generated (canonical names; M3 analogue noted for the README):**

| Canonical table | M3 analogue | Grain | Key fields |
|---|---|---|---|
| `customer_orders` | OOHEAD / OOLINE | order line | order_no, line_no, customer_no, item_no, plant, requested_date, confirmed_delivery_date, ordered_qty, ordered_weight_lb, uom |
| `deliveries` | delivery / invoice lines | order line | order_no, line_no, issue_date, invoiced_qty, invoiced_weight_lb, lot_no |
| `items` | MITMAS | item | item_no, item_name, product_group, catch_weight_flag, shelf_life_days, std_yield_pct |
| `customers` | OCUSMA | customer | customer_no, customer_name, city, state, channel |
| `inventory_snapshots` | MITBAL / MITLOC / MITBAT | location × lot × day | snapshot_date, location, item_no, lot_no, on_hand_lb, production_date, expiry_date |
| `production_yield` | production/yield reporting | plant × line × product_group × day | run_date, plant, line, product_group, input_lb, output_lb, std_yield_pct |
| `delivery_performance_report` | a 20-column delivery performance report feed | order line | Company Name, Customer Number, … , Ordered Qty, Invoiced Qty, Case Fill Rate, On Time |

**Per-plant quirks (Project A must survive these):**

| Plant | Date format | Weight unit | Customer no. format | Other |
|---|---|---|---|---|
| PLT-01 | ISO `2026-03-04` | lb | `C000123` | clean |
| PLT-02 | US `03/04/2026` | **kg** | `123` (no prefix) | 1% missing weights |
| PLT-03 | Excel serial `46085` | lb | `CUST-0123` | 0.5% duplicated lines, item numbers with trailing spaces |

**Seeded faults (for Project A recall evals), written to `ground_truth/faults.json` with fault_id, table, row key, fault_type:** missing required field, ship date before order date, invoiced weight > 105% of ordered, unknown customer, unknown item, lot shipped after expiry, negative quantity, duplicate line, UOM mismatch.

**Seeded anomalies (for Project B detection evals), written to `ground_truth/anomalies.json` with anomaly_id, metric, segment, start_date, end_date, cause, magnitude:**

| # | Metric | Segment | When | Planted cause |
|---|---|---|---|---|
| A1 | OTIF | lane PLT-02 → retail customer C000031 | 3 weeks, month 7 | late issue dates from PLT-02 |
| A2 | Fill rate (weight) | product group "case-ready" at PLT-01 | 2 weeks, month 9 | short weights |
| A3 | Yield variance | PLT-03 line L2, primals | 10 days, month 11 | output_lb depressed |
| A4 | Inventory age | warehouse DC-East, two lots | month 14 | lots not moving toward expiry |
| A5 | OTIF | all plants | 4 days, month 16 | holiday dip — **a decoy** the detector should down-weight via seasonality |
| A6 | Backlog | PLT-02 | month 17 | order surge |

Plus **noise anomalies** below threshold to test precision.

**Schema drift events (for Project A drift evals), `ground_truth/drift.json`:** month 12, PLT-02 renames `cust_no` → `customer_number`; month 15, PLT-01 adds a `lot_no` column and the business declares it required (this is the **mid-project change request** from Playbook §9.4).

### 1.4 Definition of "production-level" used throughout

A project is production-level for portfolio purposes when all of the following are true:

1. Deployed at a public URL with `/healthz` and auth on write endpoints.
2. `docker compose up` runs it locally from a clean clone in under five minutes.
3. CI runs lint, tests, and sample evals on every push; deploy is gated on green.
4. `evals/REPORT.md` exists, is generated by code, and includes failure analysis.
5. `RUNBOOK.md` lets another person operate it without you.
6. README answers the six playbook questions (Appendix B).
7. Every consequential action has a human approval gate; nothing writes to a system of record automatically.
8. Secrets are in env only; `.env.example` is committed; nothing sensitive in git history.

### 2.1 Discovery brief — PUBLIC version (Playbook Appendix A)

| Field | Entry |
|---|---|
| **Customer** | Prairie Bend Foods (fictional): multi-plant North American protein processor, ~1,200 employees, Infor M3 ERP |
| **Users** | Supply-chain analysts (2), BI developer (1), plant operations leads (3), VP Supply Chain (consumer of reports) |
| **Current workflow** | M3 extracts feed two BI tools. Tool 1 (a legacy report suite) has hand-maintained SQL per report. Tool 2 (a newer dashboard tool) rebuilds metrics independently. A shared inbox receives "this report looks wrong" tickets; an analyst reconciles by hand in a spreadsheet. |
| **Pain point** | The two tools report different OTIF for the same week; refreshes break silently when an M3 extract changes; bad rows (missing weights, duplicate lines) skew totals. Roughly a third of BI tickets are data-definition disputes rather than genuine report bugs. *(Illustrative framing for the fictional customer; no real ticket data.)* |
| **Systems involved** | Infor M3 (orders, deliveries, items, customers, inventory), plant scale/WMS exports, two BI tools, a ticketing system |

### 2.3 Architecture

```
                 ┌──────────────────────────────────────────────────────────┐
  Sources        │  sources/                                                │
  (adapters)     │   synthetic/   m3_extract (CSV per plant)                │
                 │                report_feed (20-col delivery report)      │
                 │                plant_scale (mock REST, catch weights)    │
                 │   m3_ion/      (future: real M3 adapter — same interface)│
                 └───────────────┬──────────────────────────────────────────┘
                                 │  POST /ingest/{source}  (Idempotency-Key)
                                 ▼
   ┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
   │ 1 PROFILE    │───▶│ 2 MAP        │───▶│ 3 VALIDATE   │───▶│ 4 PUBLISH    │
   │ pandas stats │    │ LLM proposes │    │ rules in code│    │ gold tables  │
   │ fingerprint  │    │ human confirms│   │ exception Q  │    │ consumer views│
   │ drift check  │    │ versioned    │    │ lineage      │    │ reconcile    │
   └──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
          │                    │                   │                   │
          ▼                    ▼                   ▼                   ▼
   bronze.raw_*        ops.mapping_versions   silver.* + ops.exceptions   gold.* + ops.reconciliation
                                 ▲
                       Streamlit portal: upload → findings → confirm mapping → exception queue → drift alerts
```

**Metric dictionary** (`metrics/*.yaml`, versioned, compiled to SQL) sits beside the pipeline and is the single definition both consumer views use.

### 2.4 Features

| # | Feature | Implementation | Playbook principle |
|---|---|---|---|
| A1 | **Source adapters** | `SourceAdapter` protocol: `discover() → fetch(batch) → fingerprint()`. Three synthetic adapters ship; interface is the seam for a real M3 adapter | §9.2 |
| A2 | **Profiling** | Per column: dtype guess, null %, distinct %, min/max, date-format detection, unit inference (lb/kg by magnitude + header), duplicate-key rate. Emits `findings.md` + JSON | §9.2 |
| A3 | **Metric dictionary** | YAML per metric with `version`, `grain`, `definition`, `owner`, `changed_by`, `effective_from`. Compiler renders SQL views. Example below | §2.1 discovery brief |
| A4 | **AI-assisted mapping** | LLM receives: source profile + canonical schema + past confirmed mappings for similar sources. Returns JSON `{source_col → canonical_col, confidence, rationale, transform}` validated by Pydantic. **Heuristic fallback** (name similarity + dtype + value patterns) runs first and always; LLM improves on it. Human confirms in portal. Every mapping is a row in `ops.mapping_versions` | §9.3 — AI proposes, never silently rewrites |
| A5 | **Validation rules** | `rules/*.py`, each with id, severity, message, suggested fix. Run in code after mapping. Rule ids V001–V012 (below) | §7.3A, §8.3 — deterministic control outside the model |
| A6 | **Exception queue** | `ops.exceptions(exception_id, batch_id, rule_id, row_key, reason, suggested_fix, owner, status)`. Portal view with assign / resolve / re-run. Nothing dropped silently | §9.2 |
| A7 | **Idempotent ingest API** | `Idempotency-Key` header stored with request hash; replay returns the original result; batch_id per run; safe re-run after failure | §9.3 hardening |
| A8 | **Lineage** | `ops.lineage(gold_table, gold_col, silver_col, mapping_version, source, source_col)` — lets drift name exactly which report breaks | §9.3 |
| A9 | **Drift detection** | Fingerprint = hash of sorted `(col, dtype, null_bucket, pattern_class)`. On change: diff → walk lineage → produce "mapping M-0042 for PLT-02 `cust_no` broken; affects gold.fact_delivery, consumer views: otif_v3" → block publish + alert | §9.3 |
| A10 | **Reconciliation** | Two consumer views computed independently from gold via the compiled dictionary + one **legacy view** using the old definition on purpose. Nightly job compares OTIF/fill rate across all three per period → `ops.reconciliation` with deltas; portal shows green/red | §2.1 discovery brief |
| A11 | **Change absorption** | The month-15 "lot_no becomes required" event is handled by adding a canonical column + a rule + a dictionary bump — no report rewrite. Time it; report it | §9.4 |
| A12 | **Access levels** | Portal roles: `viewer`, `analyst` (can propose), `owner` (can confirm mapping, resolve exceptions). Enforced server-side | Project 1 §6.3 |

**Metric dictionary example (`metrics/otif.yaml`):**

```yaml
metric: otif
version: 3
owner: supply_chain_analytics
effective_from: 2026-09-01
grain: order_line
inputs:
  on_time:  "issue_date <= confirmed_delivery_date"
  in_full_count:  "invoiced_qty >= ordered_qty"
  in_full_weight: "invoiced_weight_lb >= ordered_weight_lb * (1 - tolerance_weight)"
params:
  tolerance_weight: 0.02          # catch-weight items
rules:
  in_full: "in_full_weight if catch_weight_flag else in_full_count"
  otif:    "on_time and in_full"
aggregations:
  otif_rate: "sum(otif) / count(*)"
notes: "v3 switched catch-weight items from count to weight basis. v2 used count for all items."
```

### 2.6 Failure cases to demonstrate (Playbook Appendix C)

| Case | Expected behaviour |
|---|---|

### 2.8 Interview narrative — the five questions you must answer cold

1. **Why filter/validate before publishing rather than clean up in the report?** Because the report is the last place you find out. A bad row that reaches gold has already lied to two dashboards.
2. **Why is the LLM allowed to propose mappings but not apply them?** A mapping is a business decision with an audit trail. The LLM reads column names well; it has no authority. Wrong mappings are the highest-cost silent failure in integration work.
3. **Why a heuristic mapper at all if you have an LLM?** It's the floor, it's free, it runs when the LLM is down or wrong, and it gives you a baseline to measure the LLM's lift honestly.
4. **What happens when the source changes?** Fingerprint → diff → lineage walk → named breakage → publish blocked. Compare that to the old world: dashboard goes blank on Monday.
5. **What would you change before production?** Delta/Databricks for scale, a real M3 adapter via ION API or data lake, SSO, data contracts with source owners, alert routing, and retention policy for bronze.

**Interview keywords:** canonical schema · data profiling · schema fingerprinting · lineage · idempotency · exception queue · versioned mappings · semantic layer · reconciliation · deterministic validation · heuristic baseline · human confirmation.
