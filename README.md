# M3 Supply-Chain Command Center

**All data in this repository is synthetic, and the customer — Prairie Bend Foods — is fictional.**

> Every morning: what changed, why it matters, what to do next. Code computes every number, a model writes the
> explanation with a citation on every claim, and a person approves before anything is sent or created.

This is the second of two repositories. [`m3-trusted-data-foundation`](https://github.com/shekhus/m3-trusted-data-foundation)
produces the governed gold tables; this one consumes them. It also generates its own gold from the same world,
so it runs and demonstrates standalone.

---

## 1. Who is the customer?

Prairie Bend Foods, a fictional multi-plant protein processor running Infor M3. Three plants, two distribution
centres, ~30 customers, ~80 items. Protein makes this harder than most supply chains: items are **catch
weight** (an order for 100 cases is an order for approximately 2,000 lb, and the difference is the metric),
shelf life is measured in days, and the same customer is served from different plants on different days.

Its readers are a VP of supply chain, three plant operations leads, a logistics manager, and a BI developer who
receives the tickets.

## 2. What was broken?

Leaders opened eight to ten dashboards each morning. When something looked red, somebody investigated by hand,
decided whether it mattered, and raised a ticket or emailed a plant. Time from signal to action: often days.
Red numbers were noticed late or not at all, the investigation was manual, and the same three questions were
answered inconsistently every morning.

The specific failure this project was built around: **a lane-level collapse is invisible in the numbers
everybody watches.** One customer's OTIF at one plant falls from 93% to 48% for three weeks, and the company
total never moves outside its own noise. There is a test that asserts exactly that
(`test_the_company_total_never_sees_the_lane_collapse_at_all`).

## 3. What did you build?

```
gold.*  →  metrics/sql → metrics.daily_*     seven daily series, computed in SQL
        →  detect/       baseline · policy thresholds · CUSUM → severity → attribution
        →  pack/         the evidence pack: every quotable number, rounded once, named
                         and filtered to what this reader may see
        →  narrate/      the model writes; a validator checks every number against the pack;
                         one correction; then a templated brief that always ships
        →  act/          actions drafted in code, judged by policy.yaml
        →  graph.py      LangGraph, paused at interrupt_before=["execute"]
        →  console/      a person approves, edits or rejects
        →  deliver/      email or Slack, linking back to the console
```

Nothing writes to M3. The destinations are a ticket tracker and a note.

## 4. How do you know it works?

Everything below is regenerated by `make eval` into [`evals/REPORT.md`](evals/REPORT.md).

| Measure | Result | Target |
|---|---|---|
| Detection recall (WARN+) | **100%** | ≥ 90% |
| Detection precision (HIGH events) | **80%** | ≥ 80% |
| Attribution top-1 | **100%** | ≥ 85% |
| Holiday decoy raised as an incident | **0 times** | 0 |
| Median lead time | **1 day** | reported |
| Citation coverage | **100%** | 100%, hard gate |
| Briefs valid on the model's first attempt | **90%** | reported |
| Briefs that fell back to the template | **0%** | reported |
| Cost per brief | **$0.0019** | reported |
| Adversarial actions blocked by the policy gate | **all** | all |

Two of those deserve their caveats, which the report states in full: precision counts every HIGH event with no
seeded anomaly behind it as wrong, and the generator promises nothing about the other 529 days — so it is a
floor, not an estimate. And the detection floors in `policy.yaml` were tuned on the first half of the history;
the **held-out half, never used for tuning, scores 100% precision** and is reported separately for that reason.

The world contains a deliberate decoy: a real OTIF dip over the 4 July shutdown. A detector without holiday and
day-of-week awareness raises it as an incident and loses precision. This one reports it and caps it at WARN —
and a test asserts that the same detectors with the holiday list emptied *do* raise it, so the decoy is a real
test rather than a claim.

## 5. What would you change before production?

- **Real integrations:** Jira with SSO rather than an API token, Teams or Slack with proper app auth, and the
  metric layer reading Project A's gold instead of the standalone generator.
- **Alert routing and on-call.** `/ops/summary` names its alerts after RUNBOOK sections, but nothing pages
  anybody yet.
- **Detector drift monitoring.** The baseline ages with the business; nothing currently watches whether the
  thresholds still mean what they meant in March.
- **A better backlog measure.** There is no HIGH rule for backlog because the measurement showed a z-score
  cannot separate a real surge (z = 2.81) from ordinary swings (z up to 5.04). Level against throughput, or
  week-over-week at the same weekday, would probably work — that is a week of analysis, not a guess.
- **Cost caps and a model-change regression suite.** `make eval` is the suite; it is not wired to a budget.
- **Retention.** Packs are kept whole forever; that is right for an audit and wrong for a disk.

## Quickstart

Requires Python 3.12, and Docker for the full stack.

```
uv venv --python 3.12
uv pip install -r pyproject.toml --extra dev
cp .env.example .env

make synth-gold     # the world, its seeded anomalies and the answer key (deterministic)
make up             # Postgres (5433) + API (8010) + console (8511)
make migrate
make metrics        # gold -> metrics.daily_*
```

Then build a brief and look at it:

```
python scripts/morning.py --date 2025-09-15 --no-deliver
make console        # http://localhost:8511
```

With `LLM_PROVIDER=none` the brief uses its templated fallback, which is a supported path rather than a
degraded one — every claim is still cited and validated. With `JIRA_MODE=mock` (the default) approving an
action writes to `ops.mock_jira`, so the whole loop runs with no external accounts at all.

## Commands

```
make synth-gold     # generate data/gold + ground_truth/anomalies.json
make migrate        # apply db/migrations
make metrics        # load gold and compute metrics.daily_*
make detect DATE=   # detectors + attribution for one day, no LLM
make replay         # day-by-day detection scored against ground truth -> evals/REPLAY.md
make brief DATE=    # build a brief and stop at the approval pause
make eval           # the full evaluation -> evals/REPORT.md
make test
make lint
```

## How it is put together

| Directory | What lives there |
|---|---|
| `synth/` | the generator: one world, six seeded anomalies, an answer key, a self-check that fails the build if an anomaly is missing |
| `metrics/` | numbered plain SQL, one file per metric, merged by key so a rerun is idempotent |
| `detect/` | three detectors, severity, and the rate/mix attribution that names the driver |
| `pack/` | the evidence pack and the permission filter |
| `narrate/` | the contract, the prompt, the validator, the templated fallback |
| `act/` | drafting, the policy gate, the Jira adapter, the durable record |
| `replay/`, `evals/` | scoring against the answer key, and the generated reports |
| `docs/` | the plan, the decisions log, and [the runbook](docs/RUNBOOK.md) |

## The rules it is built on

1. The model narrates the truth; it never calculates it. No LLM call exists in `metrics/` or `detect/`, and a
   test enforces it.
2. Every claim cites a metric, and every number is checked against the pack that produced it.
3. Stale data is disclosed, never narrated over.
4. Policy lives in `policy.yaml` and is enforced in code. It is never widened from a prompt.
5. A person approves before anything executes — enforced by a graph that cannot reach the node that acts.
6. Permission filtering happens before the model call: another plant's numbers are absent from the pack, not
   hidden in the UI.
7. The brief always ships. A missing brief is a silent failure.
8. Nothing posts to the ERP. Ever.

Why each of these exists, what was measured, and what was rejected: [`docs/decisions.md`](docs/decisions.md).
